# Rules: Evaluation

## Status
These rules govern how metrics are computed, recorded, and reported. They are **mandatory**.

---

## RULE-EV01: Measured vs Derived vs Qualitative — Always Label

Every reported value must be clearly categorised as one of:
- **Measured**: directly counted or timed from pipeline output (`len(keypoints)`, `time.perf_counter()`)
- **Derived**: mathematically computed from measured values (`inlier_ratio = inliers / raw_matches`)
- **Qualitative**: assessed by visual inspection (`"panorama has visible seam near image 2 boundary"`)

**Prohibited**: Mixing these categories or leaving the status ambiguous (e.g., an "estimated" keypoint count when you could measure it exactly).

---

## RULE-EV02: All Six Required Metrics Must Be Reported

For every experiment run, every method, every image pair, report all six metrics from REQ-14:

| Metric | How to measure |
|---|---|
| 1. Detected keypoints | `len(keypoints)` per image |
| 2. Initial matches | `len(good_matches)` after ratio test / cross-check |
| 3. RANSAC inliers | `np.sum(mask)` where mask is from `findHomography` |
| 4. Inlier ratio | `inliers / initial_matches` |
| 5. Processing time | `time.perf_counter()` end - start (total pipeline) |
| 6. Panorama quality | Visual assessment (labelled as qualitative) ± SSIM if computed |

**Missing any of these metrics for any trial is a violation of REQ-14.**

---

## RULE-EV03: Timing Must Include All Stages

The "processing time" metric must be the total of all pipeline stages:
- Detection + description time
- Matching time
- RANSAC time
- Warping time
- Stitching time (for panorama trials)

Record each stage time separately and report total. Do not report only the detection time as "processing time."

---

## RULE-EV04: No Post-Hoc Parameter Tuning to Improve Results

**Prohibited**:
- Running an experiment, seeing poor results, changing RANSAC threshold, re-running, and reporting only the better result
- Selectively reporting only the trials where the algorithm succeeded

**Required**:
- Parameters are set in `experiments/config.py` before experiments are run
- All trials are reported regardless of outcome
- If parameters are changed for a legitimate reason, this is documented and the change is part of a clearly labelled separate experiment

---

## RULE-EV05: Inlier Ratio Computation Consistency

The denominator of inlier ratio must be consistent across all experiments:

```python
# Standard definition for this project:
inlier_ratio = num_ransac_inliers / num_good_matches
# Where num_good_matches = matches after ratio test / cross-check, BEFORE RANSAC
```

Do not use raw (pre-filter) match count as the denominator in one experiment and post-filter in another.

---

## RULE-EV06: Panorama Quality Assessment Protocol

For qualitative panorama quality assessment, use this consistent checklist and record each item:

```python
quality_assessment = {
    'seam_visible': False,       # Is a seam line visible? True/False
    'ghosting': False,           # Is ghosting (double exposure) present? True/False
    'colour_mismatch': False,    # Is there a colour/brightness jump at the seam?
    'misalignment': False,       # Do scene elements fail to align across the seam?
    'black_holes': False,        # Are there unfilled black regions?
    'overall_quality': 'good',   # 'good', 'acceptable', 'poor'
    'notes': '',                 # Free-text notes about specific artefacts
}
```

This checklist must be completed for every panorama result. The assessment must be done by visual inspection — it cannot be automated without a reference image.

## RULE-EV07: SSIM Computation (When Applicable)

SSIM can be computed in the overlap region between two images when both images are known to represent the same physical patch:
- Valid for: pairwise stitch where the overlap region is clearly defined
- Valid for: synthetic experiments where the true transformation is known

```python
from skimage.metrics import structural_similarity as ssim

def compute_ssim_in_overlap(img1_patch: np.ndarray, img2_patch: np.ndarray) -> float:
    """
    Compute SSIM between two corresponding image patches.
    Both must be the same shape.
    """
    if img1_patch.shape != img2_patch.shape:
        raise ValueError("Patches must be the same shape for SSIM")
    
    # Convert to grayscale for SSIM
    gray1 = cv2.cvtColor(img1_patch, cv2.COLOR_BGR2GRAY) if len(img1_patch.shape) == 3 else img1_patch
    gray2 = cv2.cvtColor(img2_patch, cv2.COLOR_BGR2GRAY) if len(img2_patch.shape) == 3 else img2_patch
    
    score, _ = ssim(gray1, gray2, full=True)
    return float(score)
```

Label SSIM clearly as a derived quantitative metric in the report.

## RULE-EV08: Comparison Table Must Be Programmatically Generated

The method comparison table in the report must be generated by code:

```python
# experiments/compare_methods.py

import pandas as pd

def generate_comparison_table(results_csv_paths: list, output_path: str):
    """
    Aggregate results from multiple experiments and generate comparison table.
    """
    dfs = [pd.read_csv(p) for p in results_csv_paths]
    combined = pd.concat(dfs, ignore_index=True)
    
    # Pivot table: method × condition × metric
    pivot = combined.groupby(['experiment', 'method']).agg({
        'num_kp_img1': 'mean',
        'num_good_matches': 'mean',
        'num_ransac_inliers': 'mean',
        'inlier_ratio': 'mean',
        'time_total_s': 'mean',
    }).round(3)
    
    pivot.to_csv(output_path)
    print(f"Comparison table saved to {output_path}")
    return pivot
```

Do not manually construct the comparison table in a spreadsheet.

## RULE-EV09: Distinguish "No Matches" from "RANSAC Failure"

These are different failure modes and must be recorded separately:

- **No matches**: `len(good_matches) < 4` — pipeline terminates before RANSAC
- **RANSAC failure**: `len(good_matches) >= 4` but `H is None` or `inliers < min_inliers`

Both are valid but different failures. Record the specific failure code in every trial.

---

## RULE-EV10: Report Mean and Standard Deviation for Non-Deterministic Metrics

RANSAC is internally stochastic. For the same input, different runs may produce slightly different inlier counts. For the baseline and primary comparison:
- Run each trial **at least 3 times**
- Report **mean ± std** for stochastic metrics (inlier count, inlier ratio)
- Report the minimum number of runs in the experiment config

For deterministic stages (detection, description, deterministic matching), a single run is sufficient.
