# Rules: Research and Academic Integrity

## Status
These rules govern academic conduct throughout the project. They are **non-negotiable**. Violations constitute academic misconduct.

---

## RULE-R01: No Fabricated Results

**Absolutely prohibited**:
- Reporting a keypoint count you did not measure
- Reporting an inlier ratio that does not match the actual pipeline output
- Showing a panorama result that was generated by a different method than claimed
- Copying numbers from a research paper and presenting them as your experimental results

**Required**:
- All numbers in tables must come from `results/*.csv` files generated by the actual running code
- All figures must be generated by the code, not created manually

---

## RULE-R02: No Fabricated Citations

**Prohibited**:
- Citing a paper you have not read (even if you found its title in another paper)
- Citing a URL that contains AI-generated content as if it were a peer-reviewed source
- Listing references in the bibliography that are not cited in the text
- Citing your own speculation as if it were from an external source

**Required**:
- Every citation must refer to a source you have genuinely engaged with
- If you are unsure about the details of a source, say so ("this method was introduced in X, though a full reading of the paper is beyond the scope of this project") — or simply don't cite it
- Only cite peer-reviewed papers, established textbooks, or official documentation

---

## RULE-R03: No Overclaiming

Do not claim properties or results beyond what was experimentally demonstrated.

**Prohibited**:
- "SIFT is the best feature detector" — you tested it on one scene under specific conditions
- "Our system achieves real-time performance" — unless you measured frame rate on the target platform
- "ORB failed completely under illumination change" — unless you measured this and it is reflected in the data

**Required**:
- Qualify all claims with scope: "Under the tested conditions of...", "On the three-image baseline dataset..."
- Use measured values: "SIFT achieved a mean inlier ratio of X.XX on the rotation experiment"

---

## RULE-R04: Clearly Attribute All External Code

If any code segment is adapted from an external source (tutorial, OpenCV documentation, Stack Overflow, textbook):
1. Include a comment in the code: `# Adapted from: [source URL or reference]`
2. Mention in the report: "The canvas size computation approach was adapted from [source]"

**What counts as your own work**: The pipeline architecture, experimental design, parameter choices, analysis, and report writing.

**What must be attributed**: Specific algorithms from papers (attribute to the paper), code snippets adapted from documentation or tutorials.

---

## RULE-R05: Plagiarism Prohibition

**Prohibited**:
- Copying text from the examination question into the report as your own writing
- Copying text from a textbook or paper without quotation marks and citation
- Submitting another student's work
- Using AI text generation to write the report and submitting it without disclosure

**Required**:
- All report text is written by the student/researcher
- If AI tools were used for drafting, this must be disclosed and the work verified for accuracy

---

## RULE-R06: Ground Truth Honesty

When comparing against "ground truth" in synthetic experiments:
- Ground truth homographies for synthetic transformations can be computed analytically — this is legitimate
- Do NOT compute a "ground truth" by running a different algorithm and using its output as ground truth
- Do NOT call visual inspection "ground truth verification"
- DO clearly label what is ground truth and what is estimated

---

## RULE-R07: Limitations Must Be Stated Honestly

A project that only shows successful results is suspicious. The report must contain a genuine limitations section that:
- Identifies the conditions under which the pipeline fails or degrades
- Explains the algorithmic reason for those limitations
- Does not downplay failures as "minor issues"

---

## RULE-R08: Experimental Methodology Transparency

For every experiment, you must be able to answer:
- What images were used?
- What parameters were used?
- How were the images generated (real vs synthetic)?
- What seed was set?
- How many trials were run?
- Were there any anomalies in the data?

This information must be recorded in `experiment_config.json` for each experiment.

---

## RULE-R09: No AI-Generated Results

Using a generative AI to produce images, panoramas, or experimental results that are then presented as real experimental outputs is prohibited.

AI tools may be used for:
- Understanding algorithms (explaining concepts)
- Drafting code structure (but code must be tested and understood)
- Proofreading report text (but substance must be your own)

AI tools must NOT be used for:
- Generating experimental result numbers
- Creating "example" panorama images that are not from the actual pipeline
- Generating a "demonstration" figure from a model rather than your own code

---

## RULE-R10: Code Must Be Understood, Not Just Working

Before submission, you should be able to answer the following questions about every major component:
1. What does this function do? (Line-by-line if asked)
2. Why was this parameter chosen?
3. What would happen if this parameter were changed?
4. What failure mode does this handle?
5. How does this function relate to the mathematical concept from the course?

If you cannot answer these questions, you do not own the code — you have copy-pasted without understanding.
